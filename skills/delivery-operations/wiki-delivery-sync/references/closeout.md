# Evidence-bound closeout

Closeout is a wiki write for one already delivered change. Confirm the selected wiki, adopting project and single writer, including ownership of shared `STATE.md` and `hot.md`. A terminal message, passing local tests, local archive, or PR status alone cannot establish shipping. An unfinished integration remains in the release train.

## Verify the sources before editing

1. Read the actual implementation and record-only closure integration readbacks from the adopting project. Resolve the full change name, accepted issue identity (or policy-approved null), implementation integration SHA, exact verified revision, accepted target SHA and the native dated archive at that target. Check the exact candidate/review and retained gate/lineage evidence required by the adopting policy. Use the actual implementation integration SHA as `shipped_commit`; use the closure integration's recorded UTC date for the wiki archive filename. Keep the verified and closure SHAs in the evidence link or reference as appropriate.
2. Read immutable receipt bytes from the verified archive or other policy-selected retained source. Compute SHA-256 of the raw bytes and match the retained acceptance and target readback. Use the adopting policy's receipt verification, including exact committed receipt path and any lineage, checkpoint and readback pins required by that policy. For `openspec-delivery`, use its read-only `change-guard.mjs receipt` procedure with the actual accepted target and archived receipt (see its [guard instructions](https://github.com/grewety/ai-coding-agent-skills/blob/main/skills/software-development/openspec-delivery/references/guard.md)). Require positive verification of matching change, issue, integrated and verified revisions, archive and receipt hash. Verify acceptance and any required cleanup separately. Stop before wiki writes if evidence is absent, stale, changed, untrusted or inconsistent.
3. Choose the canonical wiki archive target `briefs/archive/YYYY-MM-DD-<full-name>.md` and identify the active brief, all lane links, shipped row, log event, navigation, checkpoint pair and any durable decision entries for that full identity. Compare filenames, frontmatter and existing history. Confirm the same issue binding and required provenance. Find all copies, including differently dated archives and case aliases. Revalidate file paths under the vault and check current contents before writing. Refuse conflicting bytes/identity, changed receipt, unexpected duplicates or unexplained archived copies. A state entry for a newer change is independent history; preserve it.

## Apply and read back

1. Under the same writer, prepare the expected updates from verified evidence. Retain the active brief's substantive content and original identity. Add `status: archived`, `shipped_commit`, `receipt_sha256` and the evidence reference; keep its last lane as history and set the update date from the verified closeout event. Create the archive exclusively or verify an existing copy against these fields and the retained brief. Read back the complete archive before removing a still-present active copy. If both exist after an interruption, remove only the positively matched active copy, after comparing the retained content apart from the expected closeout fields and verifying the archived file. If the brief is already archived and the active file is absent, resume from the verified archive. If neither exists, or the copies disagree, preserve existing records and stop.
2. Upsert the exact full-change row in [SHIPPED.md](../templates/shipped.md) and one completed event in `log.md`, keyed by full name and receipt hash. Keep a matching row/event once; if a row or event under the same identity disagrees, stop before editing. Link to the archived brief and stable authoritative evidence; use confirmed commit permalinks when available. Remove the matched active lane link in `TRAIN.md` and keep the navigation to shipped history. Update the vault index's project/shipped navigation and, where present, redirect the exact active-brief link to its archive. Use relative Markdown links for internal navigation and verify their resolved files.
3. Update the targeted change's `STATE.md` and `hot.md` checkpoint under one writer. Use the same change, phase, disposition, UTC time, evidence, authority boundary, monitor disposition and next safe action in both. Mark shipping from the verified records. If required cleanup is pending after verified shipping, record that disposition and defer the terminal completion claim. Preserve any newer/unrelated checkpoint and current hot selection; update only links or entries for the target. Read both back and reconcile a partially written pair before future dispatch.
4. Promote only durable decisions supported by the accepted records (policy or design that should outlive this release). Use the [decisions index](../templates/decisions.md) with a stable decision heading or note link and the exact source change/evidence. Preserve pre-existing decisions and avoid daily observations, task details and private host settings. A matching decision entry is reused; a conflict is surfaced.
5. Reopen the archive, shipped row, log, train, state, hot, index and any changed decision entries. Verify exact identity, receipt, commit, link targets and single-entry counts, and that the active brief and lane link are gone. Compare the checkpoint pair where it applies. Keep each file replacement atomic where available, check for intervening edits, and treat partial writes as a pending closeout. On replay run the evidence and conflict preflight again, repair only the missing updates, and avoid changing dates or adding duplicate entries merely because the replay is later.
